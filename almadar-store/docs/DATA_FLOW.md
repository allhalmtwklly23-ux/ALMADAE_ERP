# تدفق البيانات — مسودة المرحلة B

**الحالة:** مسودة للمراجعة والاعتماد  
**المرجع:** [معمارية النظام](./SYSTEM_ARCHITECTURE.md)

## دورة الطلب

1. يرسل المتصفح طلباً إلى API دون أي سر قاعدة بيانات.
2. يتحقق الخادم من الجلسة النشطة وحالة المستخدم وكلمة المرور الأولية والمنشأة المحددة.
3. يتحقق الخادم من صلاحية الفعل ونطاق السجل وقواعد المنشأة، ثم يتحقق من بنية المدخلات.
4. تستدعي API خدمة المجال المختصة؛ الخدمة لا تثق بالمعرفات أو المجاميع المحسوبة في المتصفح.
5. تنفذ خدمة المجال التغيير داخل معاملة عند وجود أكثر من أثر مترابط، وتعيد النتيجة المعتمدة من قاعدة البيانات.
6. يسجل سجل التدقيق الفاعل والمنشأة والفعل والسجل والقيم المتغيرة والنتيجة.
7. تنشأ إشعارات/رسائل التكامل عبر Outbox داخل المعاملة؛ ترسلها مهمة خلفية قابلة لإعادة المحاولة.
8. تعيد API الحد الأدنى من البيانات المسموح بها، ثم تعرض الواجهة النتيجة أو خطأً صريحاً.

## أمثلة عمليات

### فاتورة بيع

عميل/منتجات ← تحقق صلاحية البيع والمخزون ← تحقق السعر والخصم والضريبة على الخادم ← حفظ مسودة ← مسار الموافقة حسب السياسة ← الترحيل الذري للمستند وحركة المخزون والقيد المالي ← سجل تدقيق وإشعار.

الإلغاء أو التصحيح بعد الترحيل يكون بمستند عكسي مرتبط بالأصل، لا بتعديل السجل المرحلة بصمت.

### تغيير تنظيمي

طلب تغيير بتاريخ سريان ← التحقق من صلاحية المسؤول ومنع الدورة ← حفظ علاقة جديدة بفترة فعالة ← إنهاء صلاحية العلاقة السابقة دون محوها ← تحديث العرض الحالي وفق التاريخ ← تسجيل التدقيق وإشعار الأطراف المخولة.

### تسجيل زيارة ميدانية

زيارة معيّنة ومجدولة ← موافقة صريحة على الموقع عند الوصول فقط ← إرسال الإحداثيات مرة واحدة ← حساب المسافة على الخادم مع حفظ دقة الموقع والوقت والنتيجة ← المطابقة أو المراجعة وفق حد تعتمده الإدارة ← إشعار المخولين.

لا يحدث تتبع مستمر أو جمع موقع خارج المهمة المعتمدة.

## الاتساق وإعادة المحاولة

- تستخدم العمليات المالية والمخزنية معاملات قاعدة البيانات وقيود uniqueness عند الحاجة.
- تكون العمليات التي قد يعاد طلبها آمنة عبر idempotency key.
- تستخدم الرسائل والأحداث الخارجية نمط Outbox لتجنب نجاح قاعدة البيانات وفشل الإشعار بصمت.
- لا تقبل المجاميع من العميل؛ يعاد حساب الضريبة والرصيد والحدود على الخادم.
- حالات الفشل تظهر للمستخدم وتُسجل تقنياً دون تسجيل أسرار أو كلمات مرور.

## التقارير والتحليلات

تقرأ التقارير من سجلات فعلية ومصرح بها، مع تحديد الفترة والمنشأة ومصدر الرقم. تخضع عمليات التصدير لنفس الصلاحيات، وتوضح المؤشرات غير المتوفرة بدلاً من استبدالها بأرقام افتراضية.

## التحقق قبل التنفيذ

تفاصيل مخطط الجداول والعلاقات وخطة الترحيل موثقة في [تصميم نموذج البيانات](./DATA_MODEL.md) بانتظار اعتماد مخرجات المرحلة D. يلزم اختبار التكامل على قاعدة اختبار منفصلة قبل تطبيق أي migration على بيانات حقيقية.

## حالة التنفيذ — نواة الهيكل التنظيمي

- أضيفت `GET /api/organization` لقراءة أنواع الوحدات وأنواع الهياكل والوحدات والعلاقات ضمن الشركة المحددة في الجلسة.
- تدعم `POST` إنشاء نوع وحدة أو نوع هيكل أو وحدة أو علاقة تنظيمية، وتدعم `PATCH` تعديل السجلات وأرشفتها منطقياً أو إنهاء علاقة؛ تتطلب الأفعال صلاحيات `organization:view`, `organization:create`, و`organization:edit` على الخادم.
- إنشاء العلاقة وإنهاؤها يتمان عبر PostgreSQL RPC داخل معاملة واحدة تشمل التحقق الزمني ومنع الدورات وقيد تعدد الآباء وسجل التدقيق. العلاقات أحادية الأب تُغلق سابقاتها المتعارضة قبل تاريخ البداية، ولا يسمح الإنشاء بتاريخ ماضٍ.
- تعرض واجهة العلاقات الشجرة النافذة حسب نوع الهيكل والتاريخ، وتتيح البحث والتنقل واقتراح إعادة الإسناد بالسحب والإفلات؛ تفحص الدورة والتعارضات قبل الإرسال، مع بقاء فحص الخادم الذري هو المرجع النهائي.
- أضيفت صفحة `/organization` إلى مساحة العمل، ولا يظهر رابطها إلا لمن لديه صلاحية العرض؛ لا تعرض أرقاماً افتراضية عند تعذر تحميل البيانات، وتُعاد تهيئتها عند تبديل الشركة.
- واجهة العلاقات تدعم الإنشاء والإنهاء مع رسائل صريحة لأخطاء التعارض والدورة. منطق RPC والترحيل لم يُختبرا بعد على PostgreSQL؛ يجب التحقق من الترحيل والتزامن وعزل الشركات على قاعدة اختبار منفصلة قبل تفعيل هذه العمليات في بيئة فعلية.
- أضيف [اختبار SQL تكاملي](../supabase/tests/organization_relationships.sql) يغطي منع الدورة، استبدال العلاقة أحادية الأب، الإنهاء، حدود الشركة، وتعدد الآباء. ينفذ بياناته داخل معاملة وينهيها بـ`ROLLBACK`؛ لم يُشغّل لعدم توفر PostgreSQL محلياً، لذا يجب تشغيله فقط على قاعدة اختبار معزولة، ثم إجراء اختبار كتابة متزامنة قبل الإنتاج.
- تغطي [اختبارات منطق الشجرة](../scripts/organization-structure.test.mjs) حساب البنية حسب التاريخ، وفحوص المسودة، والبحث، والتعامل الآمن مع الدورات والوحدات متعددة الآباء؛ تُشغّل بـ`node scripts/organization-structure.test.mjs`.
- الواجهة تتطلب وضع Supabase؛ في وضع JSON تعيد `503` صريحاً ولا تنشئ تخزيناً موازياً. Migration النواة لم يُطبّق بعد، ولذلك يلزم اختبار التكامل على قاعدة معزولة قبل اعتماد التشغيل.

## حالة التنفيذ — ملفات الموظفين المستقلة

- أضيفت `/api/hr/profiles` لقراءة وإنشاء وتعديل ملفات الموظفين باستخدام صلاحيات `employees:view`, `employees:create`, و`employees:edit` على الخادم، مع نطاق الشركة النشطة من الجلسة.
- تستند الملفات إلى `erp_people`، وتبقى منفصلة عن `erp_users`؛ إنشاء الملف لا ينشئ حساب دخول ولا يطلب كلمة مرور. حقول هذه المرحلة هي الرقم الوظيفي، الاسم، البريد، الهاتف، تاريخ التعيين، والحالة الوظيفية وحالة السجل.
- أضيفت صفحة `/hr/profiles` مع بحث وإحصاءات ونموذج إنشاء/تعديل/أرشفة منطقية؛ تتاح منها وصلة مستقلة إلى إدارة حسابات الدخول الحالية في `/hr`.
- يضيف [migration ملفات الموظفين](../supabase/migrations/20261118071200_employee_profiles.sql) الرقم الوظيفي وتاريخ التعيين والحالة الوظيفية إلى `erp_people`، ويفرض تفرد الرقم داخل الشركة. تتم عمليات الإنشاء والتعديل عبر RPC بحيث يُحفظ سجل التدقيق في المعاملة نفسها. لا يسمح بحذف ملف الموظف من الواجهة.
- تغطي [اختبارات إدخال الملف](../scripts/hr-employee-profiles.test.mjs) التطبيع والحقول المطلوبة والتاريخ والبريد والحالات؛ تُشغّل بـ`node scripts/hr-employee-profiles.test.mjs`. أضيف [اختبار SQL](../supabase/tests/employee_profiles.sql) لتفرد الرقم والتدقيق ومنع الكتابة عبر الشركات، لكنه لم يُشغّل؛ لا يُشغّل إلا على قاعدة اختبار معزولة وبعد تطبيق migrations هناك.
- **حدود المرحلة:** لم يُربط الملف بحساب دخول أو بتعيين تنظيمي/منصب/مدير بعد؛ ولا يشمل هذا التغيير بيانات العنوان أو الراتب أو المستندات. لا يزال الوصول يعتمد قائمة الصلاحيات الحالية، ولم يُفعّل بعد محرك ABAC أو صلاحية خاصة للحقول الحساسة. Migration جديد وغير مطبق، وواجهات القراءة/الكتابة تتطلب قاعدة Supabase مهيأة.
