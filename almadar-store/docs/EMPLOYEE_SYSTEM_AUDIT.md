# تدقيق منظومة الموظفين والتنظيم والصلاحيات

**المشروع:** ALMADAR ERP  
**تاريخ الفحص:** 18 نوفمبر 2026  
**المرحلة:** A — الفحص فقط  
**الحالة:** التقرير أُنجز؛ لا يعني أن المنظومة المؤسسية المطلوبة قد نُفذت.

## 1. الخلاصة التنفيذية

يحتوي المشروع على أساس قابل لإعادة الاستخدام، لكنه لا يحقق بعد متطلبات إدارة شركة أو مجموعة شركات كما وردت في الطلب. الموجود حالياً هو:

- حسابات مستخدمين ومصادقة وصلاحيات مرتبطة بقائمة أدوار ثابتة.
- صفحة موارد بشرية لإدارة **حسابات الدخول ذات دور `employee`**، لا ملفات الموظفين المستقلة.
- مخطط تنظيمي عام للوحدات والعلاقات، مع واجهة إدارة لأنواع الوحدات والهياكل والعلاقات.
- ترحيل مؤسسي يتضمن جداول للأشخاص والتعيينات والمناصب والأدوار والسياسات والتفويضات.

لكن وجود جدول في ملف ترحيل لا يثبت تطبيقه على قاعدة البيانات. لم أتحقق من قاعدة فعلية أو من حالة ترحيلها. كما لم أجد في كود التشغيل استهلاكاً لمحرك الأدوار والسياسات والتفويضات المقترح في الترحيل. لا توجد حالياً منظومة مكتملة للمناطق والمهام والأوامر الإدارية أو محرك ABAC/SOD.

**التوصية:** الحفاظ على مسارات الدخول وتخزين ERP الحالية، وبناء النواة تدريجياً حول الهيكل التنظيمي ثم ملف الموظف ثم حسابه ثم التفويض؛ لا تبدأ بإنشاء جميع الواجهات والجداول دفعة واحدة، ولا تطبق الترحيل على الإنتاج.

## 2. نطاق الفحص وحدوده

شمل الفحص ملفات المصدر، ومسارات API، ومخططات الترحيل، والاختبارات والوثائق الموجودة، بما فيها [SRS](./SRS.md) و[نموذج البيانات](./DATA_MODEL.md). لم أقرأ `.env.local` أو أي أسرار، ولم أتصل بقاعدة بيانات ولم أطبق أي migration. لذا فحالة قاعدة البيانات المنشورة، ونجاح migrations عليها، وإعدادات Supabase الفعلية **غير مؤكدة**.

## 3. الوضع الحالي بحسب المجال

| المجال | الموجود في المشروع | ما لا يزال غير متحقق |
|---|---|---|
| الشركات والعضويات | `erp_companies` وحسابات مرتبطة بشركة، وعضويات نشطة متعددة الشركات/المستخدمين في migrations وطبقة الجلسة. | تخويل المجموعة لا يستنتج من عضوية شركة؛ لا يوجد إثبات من هذا الفحص لحالة قاعدة منشورة أو لاختبارات عزل شاملة. |
| الفروع والمواقع | مخطط `erp_branches` و`erp_locations` في migration المؤسسة. | لا توجد إدارة مناطق وقطاعات مبيعات/تشغيل مستقلة؛ الموقع ليس بديلاً عن المنطقة أو القطاع. |
| الهيكل التنظيمي | أنواع وحدات وهياكل، وحدات وعلاقات مؤرخة. توجد واجهة وAPI لعرضها وتعديلها، وعمليات RPC للعلاقات في migration. | الواجهة لا تعرض بعد شجرة مؤسسية متكاملة تربط الموظفين والمديرين والتعيينات، ولا تدير كل وظائف النقل والدمج والتكليف. |
| ملف الموظف | `erp_people` يحفظ اسماً وبريداً وهاتفاً وحالة، ويرتبط بحساب اختياري. توجد جداول للمناصب والتعيينات وعلاقات الإشراف في migration. | لا يوجد مسار تشغيل لإدارة ملف الموظف أو ربطه بالوحدات/التعيينات؛ حقول مثل الرقم الوظيفي والعنوان والعقد والمستندات وتاريخ الخدمة غير مكتملة. |
| حساب المستخدم | `erp_users`، كلمات مرور مجزأة ومملحة، جلسات برموز مجزأة، حالة `active` وإلزام تغيير كلمة المرور. توجد API عامة وAPI موارد بشرية. | لا توجد دورة دعوة وتفعيل أو MFA أو حالات الحساب التفصيلية أو صلاحية زمنية للحساب وإدارة الأجهزة. صفحة HR الحالية تنشئ حساباً، لا موظفاً بلا حساب. |
| الأدوار والصلاحيات | `ROLE_LIBRARY` و`RoleName` ثابتان في الشيفرة؛ صلاحيات مباشرة محفوظة للحساب/العضوية. توجد قائمة HR ثابتة لتفويض مجموعة صلاحيات HR. | جداول الأدوار والصلاحيات والنطاق والسياسات والتفويضات لا تغذي قرار الوصول في runtime؛ لا يوجد محرك ABAC أو SOD مركزي متصل بجميع APIs. |
| المسؤوليات والمهام والأوامر | بعض وحدات ERP العامة تعرض مفاهيم مشاريع/مهام أو دعم، وتوجد رسائل فريق. | لا يوجد نظام موارد موحد لمهام الموظفين وتكليف الأقسام والأوامر الإدارية ودورة اعتماد الإنجاز وسجلها الزمني. |
| التدقيق | يوجد `erp_audit_log` ومسارات تكتب أحداثاً أساسية؛ migration المؤسسة توسع حقوله. | لا يوجد إثبات لتغطية جميع عمليات الموظفين أو لذرية كل عملية حساسة مع سجل التدقيق؛ اختبارات المراجعة والتصدير محدودة. |

### 3.1 التنظيم وقاعدة البيانات

ملف [migration التأسيسي](../supabase/migrations/20261118000000_enterprise_core.sql) يحتوي على:

- المجموعة والفروع والمواقع.
- أنواع الوحدات وأنواع الهياكل والوحدات والعلاقات المؤرخة.
- الأشخاص، وعائلات ومستويات ومسميات العمل، والمناصب والتعيينات.
- علاقات الإشراف الإداري/الوظيفي.
- صلاحيات وأدوار وربطها بالعضويات، وقواعد سياسات وتفويضات.
- توسيع سجل التدقيق.

وتعرض [واجهة التنظيم](../src/components/organization-workspace.tsx) حالياً الأنواع والوحدات والعلاقات، عبر [API التنظيم](../src/app/api/organization/route.ts). هذه نواة مفيدة، لكنها ليست بعد لوحة تحكم كاملة للهيكل والموظفين. كذلك لا يحتوي المخطط الحالي على كيان مستقل للمناطق والقطاعات الجغرافية والعملاء الموزعين عليها.

### 3.2 ملفات الموظفين وحساباتهم

صفحة [الموارد البشرية](../src/app/hr/page.tsx) تعرض [لوحة حسابات الموظفين](../src/components/hr-employee-accounts-panel.tsx). هذه اللوحة تقرأ وتعدل سجلات المستخدمين ذات `role = employee` عبر [API الموظفين](../src/app/api/hr/employees/route.ts). النموذج يطلب حساب دخول وكلمة مرور، ويخزن الإدارة والقسم والمسمى كنصوص في حساب المستخدم. لذلك:

- لا يمكن حالياً تسجيل موظف لا يحتاج حساب دخول.
- لا يوجد ربط تشغيلي بين سجل `erp_people` وحساب `erp_users`.
- الإدارة والقسم والمسمى في نموذج HR الحالي ليست مراجع إلى وحدات أو مناصب تنظيمية.
- إعداد الموظف، تاريخ عمله، مديره، عقوده ومستنداته وتاريخه الوظيفي ليست جزءاً من ذلك النموذج.

يحتوي [module-config.ts](../src/lib/erp/module-config.ts) على مخطط حقول HR مثل الرقم الوظيفي والهاتف وتاريخ التعيين والراتب. لكن `employees` غير موجود في قائمة كيانات التخزين العامة في [store.ts](../src/lib/erp/store.ts)، فلا ينبغي اعتبار هذا المخطط دليلاً على وجود سجل موظفين محفوظ وقابل للاستخدام.

### 3.3 الصلاحيات والأمان

- الأدوار محددة كاتحاد TypeScript ومصفوفة `ROLE_LIBRARY` في [auth-system.ts](../src/lib/erp/auth-system.ts). ويوجد نموذج صلاحيات قديم مستقل في [access-control.ts](../src/lib/erp/access-control.ts)، لذلك يلزم توحيد مصدر الحقيقة قبل توسيع التفويض.
- `userHasPermission` و`requireDatabasePermission` يفحصان صلاحيات المستخدم المباشرة (`entity:action` وما شابه)، ولا يقرآن `erp_role_permissions` أو `erp_policy_rules` أو `erp_delegations` لتقييم سياق ABAC.
- API موارد بشرية تتحقق خادمياً من الفعل، وتقيّد الصلاحيات القابلة للمنح بقائمة ثابتة وبصلاحيات المفوّض. هذا حاجز مفيد، لكنه لا يحقق بعد إدارة صلاحيات ديناميكية قابلة للتعديل من لوحة التحكم.
- إدارة المستخدمين العامة في [API المستخدمين](../src/app/api/users/route.ts) محصورة بمدير النظام؛ أما API الموارد البشرية فمحدودة بعمليات حسابات الموظفين، وليست CRUD عاماً لكل أدوار النظام.
- اتصال قاعدة البيانات يستخدم `service_role` على الخادم، وهو يتجاوز RLS؛ لذلك يجب أن يفرض كل مسار نطاق الشركة والعضوية والصلاحية بنفسه. توجد دوال سياق شركة في [database.ts](../src/lib/erp/database.ts)، لكن هذا لا يغني عن اختبارات سلبية عبر الشركات والفروع.
- عمليات إنشاء/تعديل الحسابات وتسجيل التدقيق منفصلة في طبقة التخزين الحالية؛ يجب تصميم العمليات الحساسة القادمة لتكون ذرية أو ذات سلوك تعافٍ واضح حتى لا ينجح التغيير دون سجل تدقيق.

## 4. الفجوات ذات الأولوية

1. **مصدران مختلفان لمفهوم الموظف:** حساب الدخول يُستخدم حالياً كأنه ملف الموظف، بينما تصميم قاعدة البيانات يفصل الشخص والتعيين والحساب.
2. **مرجع تنظيمي غير مكتمل:** القسم والمسمى نصان في حساب المستخدم، ولا توجد إدارة تربط كل موظف بوحدته ومنصبه ومديره وفق تاريخ سريان.
3. **محرك الصلاحيات غير ديناميكي:** الجداول المقترحة لا تستخدمها طبقة التفويض، والصلاحيات والنماذج والأدوار المهمة معرفة في الشيفرة.
4. **نطاقات الوصول غير مطبقة مركزياً:** لا يوجد تقييم موحد للشركة/الفرع/الإدارة/الفريق/السجل/قيمة العملية قبل كل عملية حساسة.
5. **نقص إدارة المناطق:** لا يوجد نموذج نطاقات وقطاعات مستقل عن المواقع والفروع.
6. **غياب سير العمل المطلوب:** المهام والأوامر والتفويض ومراجعة الإنجاز وSOD ليست منظومة تشغيلية مكتملة.
7. **التحقق غير كافٍ للقبول النهائي:** الاختبارات الموجودة مركزة على منطق تفويض HR وشجرة التنظيم، واختبار SQL للتنظيم مصمم لقاعدة معزولة ويستخدم `ROLLBACK`. لا توجد اختبارات تكامل تغطي دورة الموظف والحساب والصلاحية والمهمة والنقل والتفويض وسجل التدقيق كاملة.

## 5. خطة التوسع الآمن دون كسر الوظائف الحالية

ينفذ التطوير تدريجياً وبترحيلات إضافية، مع إبقاء تسجيل الدخول وواجهات ERP الحالية عاملة إلى أن يثبت البديل اختبارات التكافؤ:

1. **النواة التنظيمية:** تثبيت واختبار ترحيل الهيكل في بيئة معزولة، ثم استكمال إدارة الشركات والفروع والوحدات والعلاقات والتواريخ. إضافة نموذج المناطق والقطاعات ككيانات مستقلة، لا باعتبارها أنواع مواقع فقط.
2. **ملف الموظف:** تشغيل سجل مستقل للموظف دون اشتراط حساب، وربطه بالتعيين والمنصب والفرع والوحدة وعلاقات المدير. إضافة الحقول والمستندات الشخصية بعد وضع نطاقات عرض وخصوصية واضحة.
3. **حساب الدخول:** ربط الحساب بالموظف اختيارياً، مع دورة دعوة/تفعيل وإيقاف وانتهاء وإبطال جلسات، دون عرض كلمات المرور أو كسر تسجيل الدخول الحالي.
4. **الأدوار ومحرك الصلاحيات:** بناء خدمة مركزية `can(user, action, resource, context)` على الخادم. توصيل الأدوار والصلاحيات والنطاقات والسياسات والتفويضات الفعلية بها. إبقاء `role` و`permissions` الحاليين كطبقة توافق مؤقتة حتى تكتمل تغطية APIs واختبارات الرفض.
5. **المسؤوليات والتكليفات:** تعريف المسؤوليات والأوصاف والتفويضات المؤقتة وتواريخها، مع سجل تاريخي وإبطال تلقائي عند الانتهاء.
6. **المهام والأوامر الإدارية:** إنشاء الكيانات وسجل الحالات والتعليقات والمرفقات والإشعارات؛ التحقق خادمياً من الإسناد والقبول والمراجعة والإغلاق.
7. **الربط والرقابة:** نقل كل وحدة ERP تدريجياً إلى قرار التفويض الموحد، مع قواعد فصل المهام والتدقيق ضمن معاملات حساسة.
8. **اختبارات القبول:** تغطية موظف بلا حساب، حساب معطل/منتهي، عدة شركات/فروع/أدوار، حدود النطاق، تغيير الصلاحيات أثناء الجلسة، انتهاء التفويض، API المباشر، SOD، وسجل التدقيق. لا تُعتبر ميزة مكتملة بمجرد ظهور واجهتها.

### ضوابط عدم التأثير على الوظائف الحالية

- لا تحذف أو تعِد تسمية جداول أو حقول المستخدمين القائمة في أول مرحلة.
- لا تستبدل API المصادقة أو الإدارة العامة دفعة واحدة.
- أضف migrations وجداول/فهارس ومفاتيح أجنبية تدريجياً، ثم اربط واجهات صغيرة بكل مسار.
- حافظ على عزل `company_id` في القراءة والكتابة، وتحقق من العضوية النشطة قبل أي وصول.
- لا تخزن كلمات مرور أو رموز تفعيل مكشوفة؛ ولا تضع أسراراً في السجلات.
- اختبر الترحيلات والاستعادة على قاعدة اختبار معزولة قبل اعتمادها؛ لم يُطبّق أي migration في هذا الفحص.

## تحديث التنفيذ بعد الفحص

بعد إعداد هذا التقرير، أضيفت نواة أولية مستقلة لملفات الموظفين: صفحة `/hr/profiles` وAPI محمية لقراءة وإنشاء وتعديل وأرشفة السجل الوظيفي، من دون إنشاء حساب دخول. أضيفت حقول الرقم الوظيفي وتاريخ التعيين والحالة الوظيفية بترحيل جديد، وتكتب عمليات الإنشاء والتعديل سجل التدقيق داخل معاملة قاعدة البيانات. التفاصيل وحدود هذه المرحلة موثقة في [تدفق البيانات](./DATA_FLOW.md).

اجتاز المشروع `npm run build` و`npm run lint` (مع تحذير سابق غير متعلق بالتغيير في `src/lib/erp/store.ts`) واختبارات HR الحالية واختبارات ملفات الموظفين. **لم يُطبّق الترحيل ولم يُشغّل اختبار SQL** لعدم توفر أداة PostgreSQL محلية؛ يلزم اختباره في قاعدة معزولة قبل اعتماد التشغيل. لا تزال تعيينات الهيكل والمناصب، وربط الحساب اختيارياً، ومحرك الصلاحيات الديناميكي، والمناطق والمهام والأوامر مراحل غير مكتملة.
