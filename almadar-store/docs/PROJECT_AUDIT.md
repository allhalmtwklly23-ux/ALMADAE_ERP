# تقرير تدقيق المشروع — المرحلة A

**تاريخ الفحص:** 18 نوفمبر 2026  
**النطاق:** فحص الشيفرة والإعدادات والاختبارات الموجودة فقط. لم تُعدّل وظائف النظام ولم تُنفذ أي ترحيلات لقاعدة البيانات.

## الخلاصة التنفيذية

المشروع تطبيق Next.js عربي قائم، يحتوي على شاشات ووحدات أعمال متعددة، ومجموعة وظائف تشغيلية فعلية في المبيعات والمخزون والمستخدمين والتواصل. لكنه ما زال **نموذجاً أولياً موسعاً مع أجزاء تشغيلية**، وليس منصة ERP مؤسسية مكتملة أو جاهزة للإنتاج وفق التوجيه الرئيسي. توجد فجوة واضحة بين اتساع الواجهات وبين عمق المحاسبة والهيكل التنظيمي وسير العمل والتدقيق والتكاملات.

يوصى بالحفاظ على التطبيق الحالي وتطويره تدريجياً، مع تثبيت تصميم النواة والبيانات قبل بناء وحدات مؤسسية جديدة. لم يمكن التحقق من قاعدة بيانات Supabase الفعلية أو حالة تطبيق الترحيلات، كما لا يوجد remote GitHub أو سجل commits في المستودع الحالي.

## 1. الوضع الحالي

- تطبيق ويب في مجلد `almadar-store`، يعمل ببنية App Router، ويضم صفحات عامة وصفحات ERP محمية وتطبيقات أعمال.
- توجد 10 ملفات لمسارات API، تشمل المصادقة وإدارة المستخدمين وبيانات ERP والتواصل.
- التخزين يختار بين JSON محلي وSupabase بحسب متغيرات البيئة؛ وثائق المشروع تشترط Supabase للإنتاج.
- نمط بيانات ERP في Supabase يعتمد إلى حد كبير على سجلات عامة ذات `entity` وبيانات JSONB، مع بعض جداول الدعم المنظمة.
- يوجد 6 ملفات migrations مكتوبة يدوياً. حالة تطبيقها على أي مشروع Supabase فعلي غير مؤكدة.
- حالة Git: فرع `main` بلا commits، ولا يوجد remote مضبوط. ملفات المشروع المسجلة حالياً مضافة إلى الفهرس (staged). لذلك لا يوجد ربط GitHub أو نشر تلقائي مثبت.
- `.env.local` مستثنى من Git بحسب `.gitignore`. لم تُقرأ قيم الأسرار.

## 2. التقنيات

- Next.js 16.4.2 وReact 19.3.0 وTypeScript 5.
- Tailwind CSS 4 عبر تكامل Turbopack.
- Supabase JS للتخزين والوصول إلى PostgreSQL.
- تخزين JSON محلي للتطوير عند عدم تهيئة Supabase، وفق شروط التشغيل الموضحة في README.
- فحوصات ESLint وTypeScript، و10 ملفات اختبارات JavaScript/TypeScript.
- إعداد Next.js يستخدم مجلد `.next-build` للبناء والتطوير.

## 3. الوظائف المكتملة أو العاملة جزئياً

- تسجيل الدخول والجلسات وتغيير كلمة المرور وإدارة الحسابات والأدوار المحددة مسبقاً.
- فصل بيانات المنشأة في مسارات الاستعلام والكتابة، واختيار المنشأة ضمن جلسة Supabase.
- شاشات CRUD عامة للسجلات حسب تعريفات الوحدات، مع عمليات API للتحقق من المستخدم والصلاحية.
- أجزاء عملية للمبيعات: البحث عن المنتجات والأطراف، حساب ضريبة وخصومات لفواتير المبيعات الجديدة، معاينة سجل تكلفة المنتج، وتحذيرات مخزون.
- ترحيل فاتورة البيع/الشراء في Supabase عبر دالة SQL تحدث حالة الفاتورة والمخزون في معاملة واحدة.
- رسائل مباشرة نصية بين أعضاء المنشأة، وسجل محادثة وإشعارات عدد الرسائل غير المقروءة. التحديث يتم بالاستطلاع الدوري؛ لا توجد إشعارات دفع.
- مهاجرات تأسيسية للعضويات، ورسائل الفريق، وجداول تأسيسية مستقبلية للامتثال الإلكتروني.

## 4. الوظائف غير المكتملة

- لا يوجد محرك فعلي للمجموعات والشركات التابعة والفروع والمواقع؛ دعم المنشآت الحالي لا يحقق كامل نموذج Multi-Group/Multi-Company/Multi-Branch.
- لا يوجد Organization Engine أو Job Architecture أو Workforce Assignment متكامل. حقول الإدارة والمدير المباشر موجودة محلياً في نموذج المستخدم، لكن API وخرائط مستخدمي Supabase لا تمررها أو تحفظها؛ وبالتالي لا تعمل كعلاقة مؤسسية متسقة.
- الأدوار والصلاحيات محددة مسبقاً في الشيفرة، ولا يوجد محرك سياسات RBAC/ABAC قابل للتكوين من لوحة الإدارة كما يتطلب الهدف.
- لا يوجد محرك عام لسير العمل والموافقات والتفويض والتصعيد أو مركز قيادة مؤسسي.
- صفحات الموارد البشرية والرواتب والمشاريع والصيانة والجودة والخدمات وغيرها لا تمثل بعد أنظمة المجال الكاملة، حتى عندما تتوفر واجهات إدخال عامة.
- لا يظهر تطبيق زيارات المندوبين كعملية مفعّلة؛ كتالوج التطبيقات المخططة يصرح بأن الزيارات والتطبيقات المقترحة غير نشطة.
- جداول ZATCA/e-invoice تأسيسية فقط؛ لا يوجد في نطاق التنفيذ المفحوص توليد XML متوافق أو توقيع/شهادات أو إرسال ومتابعة فعلية إلى فاتورة. توثيق README يصرح بذلك.
- لا يوجد دليل على تفعيل MFA أو استعادة النسخ الاحتياطية واختبارها، أو إعداد مراقبة وإنتاج.

## 5. الوظائف الشكلية أو البيانات غير الحقيقية

- `src/data/erp-data.ts` و`src/lib/erp/financial-engine.ts` يحتويان قيماً مالية واتجاهات وسجلات وأحداث تدقيق ثابتة، ويعيد `/api/erp` بعض هذه القيم ضمن الاستجابة العامة. يجب عدم تقديمها للمستخدم باعتبارها أرقام منشأته.
- بعض بطاقات التقارير والإعدادات تعرض أرقاماً أو تكاملات ثابتة، وليست ناتجة عن عمليات تشغيل موثقة.
- صفحة لوحة المؤشرات الحالية تقرأ بعض المجاميع من سجلات المنشأة، لكن ذلك لا يجعل القيود المحاسبية أو القوائم المالية مكتملة.
- قائمة التطبيقات المخططة موسومة بوضوح بأنها غير مفعلة؛ هذا إفصاح جيد وليس تنفيذاً وظيفياً.

## 6. الأخطاء ونتائج التحقق

- `npx.cmd tsc --noEmit`: نجح دون أخطاء.
- `npm.cmd run lint`: نجح دون أخطاء، مع تحذير واحد عن متغير غير مستخدم في أحد الملفات.
- الاختبارات العشرة الموجودة نجحت عند تشغيلها باستخدام `node --experimental-strip-types`؛ مجموعها 20 حالة اختبار تقريباً. التشغيل المباشر دون هذا الخيار يفشل في Node 22 بسبب استيراد ملفات TypeScript، ولا يوجد أمر `test` موحد في `package.json`.
- لم يُشغّل بناء إنتاجي؛ إعداد التطوير والبناء يستخدمان مجلد `.next-build` نفسه، وتجنب الفحص الكتابة فوق مخرجات قد يستخدمها خادم التطوير.
- عند بدء معاينة التطوير، أبلغ Next.js أن الإصدار الحالي متأثر بثغرة أمنية معروفة وأوصى بترقية أمنية. لم تُحدّث الحزم في هذه المرحلة.
- لم يُختبر اتصال حقيقي بقاعدة البيانات أو صلاحياتها أو migrations، ولم تُقرأ بيانات `.env.local`.

## 7. نقاط القوة

- بنية Next.js حديثة، وتقسيم معقول بين صفحات التطبيق والمكونات وطبقة ERP.
- فصل التخزين المحلي عن Supabase ووجود توثيق للاستيراد والتحويل والنسخ الاحتياطي.
- وجود تحقق خادمي للمصادقة والصلاحيات في مسارات API، واستخدام Cookie من نوع `HttpOnly`.
- استخدام `company_id` في الجداول واستعلامات Supabase، مع تفعيل RLS على الجداول الأساسية.
- ترحيل الفاتورة والمخزون يتم عبر دالة قاعدة بيانات واحدة في مسار Supabase.
- README يوضح حدود ميزات المبيعات والرسائل والامتثال، ولا يصف بعض الميزات المخططة على أنها منجزة.
- توجد اختبارات مركزة لعزل رسائل المنشآت وحساب الضريبة والبحث وسلامة تخزين المصادقة.

## 8. نقاط الضعف

- نموذج البيانات العام المبني على JSONB يضعف القيود العلائقية والاستعلامات والتقارير والتاريخ الفعال للوحدات الأساسية.
- محرك المحاسبة الحالي لا يثبت وجود دفتر أستاذ متكامل أو ترحيل مزدوج مترابط لكل حركة تشغيلية.
- صيغ صلاحيات ثابتة، ولا يوجد فصل مكتمل بين المستخدم والموظف والتعيين والمنصب والمسمى.
- اختلاف بين نموذج المستخدم المحلي وطبقة Supabase في حقول الإدارة/المدير المباشر.
- لا يوجد إعداد CI أو نشر متصل بـGitHub ضمن ملفات المشروع التي جرى فحصها.
- خطة التحقق الآلي غير موحدة: اختبارات منفصلة بلا أمر تشغيل قياسي، والبناء الإنتاجي لم يُتحقق منه.

## 9. المخاطر

1. **أمن الإنتاج — مرتفع:** تحذير Next.js الأمني يتطلب مراجعة وترقية قبل النشر. لا تستخدم التطبيق إنتاجياً قبل حل التحذير وإعادة الفحص.
2. **عزل البيانات — مرتفع الأهمية:** يستخدم التطبيق مفتاح Supabase بصلاحية service role في الخادم، وهو يتجاوز RLS؛ لذلك يعتمد العزل فعلياً على كل مسار API وسياق المنشأة وصحة الاستعلامات.
3. **محاسبي/تنظيمي — مرتفع:** البيانات المالية التجريبية، وغياب دورة دفتر أستاذ متكاملة، وعدم اكتمال ZATCA قد يؤدي إلى عرض معلومات مضللة إذا اعتُبرت نهائية.
4. **الترحيل والاستعادة — مرتفع:** لا توجد نتيجة تحقق لقاعدة حية أو خطة مثبتة لترقية البيانات الحالية واسترجاعها.
5. **النشر — متوسط/مرتفع:** لا remote أو commits؛ لا يوجد مسار موثوق لمعاينة GitHub أو تحديث تلقائي للموقع.
6. **التوسع — متوسط/مرتفع:** تخزين معظم الكيانات كسجلات JSON عامة يجعل القيود، الفهارس، المعاملات، والتقارير المتقدمة أصعب.
7. **الهوية والصلاحيات — متوسط/مرتفع:** لا يثبت الفحص تفعيل MFA أو سياسات تفويض مرنة ومصفوفة فصل المهام.

## 10. الأجزاء التي يجب المحافظة عليها

- مسارات المصادقة وإدارة الجلسات الحالية، بعد استكمال توافق نموذج المستخدم بين التخزينين.
- سياق المنشأة في جلسة Supabase والتحقق الخادمي من الصلاحيات.
- وظيفة ترحيل الفاتورة والمخزون الذرية، وقواعد حساب ضريبة/خصومات المبيعات واختباراتها.
- الرسائل الحالية وعزل المنشأة والمشاركين، مع الإفصاح عن صلاحية الإشراف الإداري.
- فحوصات أمان ملف المصادقة، وإجراءات استيراد JSON الموثقة، وعدم حذف بيانات قديمة تلقائياً.
- مكونات الواجهة العربية الحالية، مع مراجعة الوصولية والاتجاهين RTL/LTR عند توسيعها.

## 11. الأجزاء التي تحتاج إلى إعادة تصميم تدريجية

- تأسيس نموذج المؤسسة والموظفين والتعيينات كوحدات بيانات مترابطة ذات معرفات ثابتة وتواريخ سريان.
- فصل المحاسبة عن بيانات المؤشرات الثابتة، وبناء دليل حسابات وقيود مزدوجة وترحيل قابل للتدقيق.
- تحويل تعريفات الوحدات العامة إلى نماذج وخدمات مجال typed تدريجياً، مع إبقاء التوافق والاستيراد.
- بناء سياسات صلاحيات وتفويض وسير عمل مستقلة عن اسم المنصب.
- ربط التدقيق والإشعارات والوثائق بالعمليات الحقيقية وبسياسة حفظ واضحة.
- فصل بيانات النماذج والتقارير الثابتة وإظهار حالة واضحة للميزة غير المنفذة.

## 12. خطة التنفيذ وعدد المراحل

وفق التوجيه، الخطة **11 مرحلة**؛ المنجز في هذا الطلب هو تدقيق المرحلة A فقط:

1. **A — تدقيق المشروع:** هذا التقرير.
2. **B — معمارية النظام:** إعداد مخططات الوحدات وتدفق البيانات والأمن والتقنيات.
3. **C — SRS:** تحليل المتطلبات والمستخدمين والصلاحيات وسير العمل.
4. **D — تصميم البيانات:** ERD وعلاقات وفهارس وخطة ترحيل قابلة للاسترجاع.
5. **E — النواة:** Multi-tenancy والهيكل التنظيمي والمناصب والتعيينات والصلاحيات والتدقيق.
6. **F — العمليات المؤسسية:** الأوامر والمهام والمشاريع والموافقات وسير العمل والوثائق.
7. **G — وحدات الأعمال:** تنفيذ الوحدات تدريجياً وربطها بالنواة.
8. **H — العمليات الميدانية:** الزيارات والمندوبون والمناطق بموافقة الموقع.
9. **I — التحليلات والذكاء الاصطناعي:** بعد ثبات البيانات والصلاحيات.
10. **J — الأمن والجودة:** اختبارات عزل وتكامل وأداء ومراجعة أمنية.
11. **K — النشر:** CI/CD والبيئات والمراقبة والنسخ الاحتياطي والاستعادة.

كل مرحلة لاحقة تحتاج مراجعة واعتماد مخرجاتها قبل الانتقال إلى المرحلة التالية، وفق التوجيه الرئيسي.

## ملحق تحقق لاحق — 18 نوفمبر 2026

هذا الملحق يوثق تغييرات التحقق بعد إعداد التقرير، ولا يغير خط الأساس التاريخي أعلاه:

- تمت ترقية `next` من `16.4.2` إلى `16.4.6`، وتزامن `package-lock.json` مع `package.json`.
- نجح بناء الإنتاج على Next.js `16.4.6`، ونجح TypeScript، واجتازت الاختبارات 20 حالة.
- نجح lint دون أخطاء مع تحذير سابق واحد عن متغير غير مستخدم في `src/lib/erp/store.ts`.
- أظهر `npm audit --omit=dev` عدم وجود ثغرات في اعتماديات الإنتاج. أظهر التدقيق الكامل 15 تنبيهاً في اعتماديات التطوير؛ لم ينفذ `npm audit fix --force` لأنه اقترح الرجوع بإعداد ESLint إلى إصدار رئيسي أقدم.
- المعاينة المحلية على `http://127.0.0.1:3000` تعمل وتعرض شاشة تسجيل الدخول عند غياب جلسة.
- لم يُتصل بقاعدة Supabase فعلية ولم تُطبق أي migrations. ملف migration المؤسسي الجاري يحتاج اختباراً في قاعدة معزولة قبل اعتماد التشغيل.
