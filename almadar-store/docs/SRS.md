# وثيقة متطلبات النظام (SRS)

**الحالة:** معتمدة من المستخدم للانتقال إلى المرحلة D (18 نوفمبر 2026)  
**المصدر:** توجيه ALMADAR المؤسسي ومتطلبات المشروع الحالية  
**المرجع المعماري:** [معمارية النظام](./SYSTEM_ARCHITECTURE.md)، [خريطة الوحدات](./MODULE_MAP.md)، [تدفق البيانات](./DATA_FLOW.md)، [معمارية الأمن](./SECURITY_ARCHITECTURE.md)

## 1. الغرض

تحدد هذه الوثيقة متطلبات منصة ALMADAR ERP القابلة للتخصيص للمنشآت متعددة الأنشطة. وهي تصف السلوك المطلوب للنظام دون افتراض سياسة مالية أو تنظيمية لم يحددها العميل. المتطلبات ذات السياسة غير المحسومة موسومة بـ **TBD** ولا يجوز تنفيذها كتخمين.

## 2. النطاق

يشمل النطاق نواة مؤسسية واحدة، ووحدات أعمال اختيارية مترابطة عبر واجهات مجال وسير عمل وتدقيق مركزي. يهيئ العميل المنشآت والأقسام والمناصب والصلاحيات والسياسات من النظام، دون تعديل الشيفرة.

لا تعني هذه الوثيقة أن الوظائف موجودة حالياً. خط الأساس الفعلي والفجوات موضحة في [تقرير التدقيق](./PROJECT_AUDIT.md). التنفيذ يكون تدريجياً بعد اعتماد التصميم والمخطط وخطة ترحيل البيانات.

## 3. المصطلحات

| المصطلح | المعنى |
|---|---|
| المجموعة | الكيان الأعلى الذي قد يضم شركات مستقلة أو تابعة |
| الشركة | منشأة قانونية أو تشغيلية تملك سجلات ومعاملات |
| الفرع/الموقع | نطاق جغرافي أو تشغيلي تابع لشركة |
| وحدة تنظيمية | عقدة قابلة للتسمية ضمن هيكل المنشأة |
| الشخص | سجل هوية موظف مستقل عن حساب الدخول |
| المستخدم | حساب مصادقة وصلاحيات داخل النظام |
| المنصب | وظيفة تنظيمية شاغرة أو مشغولة |
| المسمى الوظيفي | وصف لغوي للوظيفة؛ لا يحدد الصلاحيات تلقائياً |
| التعيين | علاقة موظف/منصب/وحدة تنظيمية ذات تاريخ سريان |
| المستأجر | نطاق بيانات معزول تحدده سياسة المجموعة/الشركة المعتمدة |
| العملية المرحلة | عملية نهائية لا تعدل مباشرة؛ تصحح بعكس/مستند مرتبط موثق |

## 4. فئات المستخدمين

هذه فئات احتياج وليست أدواراً أو منح صلاحيات افتراضية:

1. مالك المنصة ومسؤول التهيئة المؤسسية.
2. مدير المجموعة أو الشركة أو الفرع.
3. مسؤول الأمن والصلاحيات.
4. مدير أو مشرف وحدة تنظيمية.
5. موظف/مندوب/عامل ميداني.
6. مستخدمو المالية والمبيعات والمشتريات والمخزون والموارد البشرية.
7. المراجع الداخلي ومراجع الامتثال.
8. مسؤول التكاملات والتقارير.
9. مستخدم قراءة محدود أو جهة خارجية عند إقرار الوصول الخارجي.

لا يحصل أي مستخدم على صلاحية لمجرد مسماه الوظيفي. تُحدد الأدوار والنطاقات والموافقات في إعدادات المنشأة.

## 5. الافتراضات والقيود

- المنصة Modular Monolith ما لم تثبت حاجة تشغيلية لفصل خدمة.
- PostgreSQL هو مخزن البيانات العلائقي؛ لا يستخدم JSONB بديلاً عن العلاقات والقيود الأساسية.
- كل عملية أعمال تحتاج منشأة فعالة وصلاحية نطاقية.
- إعدادات العملة والمنطقة الزمنية والضريبة والتقويم قابلة للتهيئة لكل نطاق معتمد.
- لا تطبق migrations على قاعدة فعلية قبل النسخ الاحتياطي وخطة الرجوع واختبار قاعدة منفصلة.
- لا يتتبع النظام موقع الموظف خارج المهمة المصرح بها.
- يجب أن يميز العرض بين بيانات حقيقية ومخططة أو غير متاحة.

## 6. المتطلبات الوظيفية

### 6.1 النواة المؤسسية وإدارة المستأجرين

**FR-CORE-001:** يجب أن يسمح النظام بإنشاء مجموعة وشركات وفروع ومواقع وعلاقات بينها وفق نموذج معتمد.  
**القبول:** يمكن إنشاء شجرتين مؤسسيتين منفصلتين، والتحقق من أن المستخدم لا يقرأ سجلات خارج العضوية الفعالة.

**FR-CORE-002:** يجب أن تحتوي كل عضوية على نطاق الشركة/المجموعة وحالة وتاريخ صلاحية ودور/سياسات واضحة.  
**القبول:** تعطيل العضوية يمنع الطلبات الجديدة فوراً دون حذف سجل العضوية أو المعاملات التاريخية.

**FR-CORE-003:** يجب دعم المنطقة الزمنية والعملة واللغة وإعدادات الدولة على النطاق الذي تعتمده المنشأة.  
**القبول:** تعرض المستندات والتقارير العملة والتاريخ وفق إعدادات الشركة، مع حفظ القيمة الأصلية والعملة عند الحاجة للتحويل.

**FR-CORE-004:** يجب أن يسمح النظام بتفعيل الوحدات المتاحة لكل عميل دون نسخ النواة أو تعديل الشيفرة.  
**القبول:** المستخدم غير المخول أو الوحدة غير المفعلة لا يستطيع فتح واجهة الوحدة أو طلب API الخاص بها.

### 6.2 الهيكل التنظيمي

**FR-ORG-001:** يجب تعريف أنواع ومستويات الوحدات التنظيمية من الإعدادات، وإضافة/إعادة تسمية/تعطيل/أرشفة مستوى أو وحدة.  
**القبول:** إنشاء مستوى غير موجود في القوالب لا يتطلب تغييراً برمجياً، ولا يؤدي تعطيله إلى حذف سجلاته التاريخية.

**FR-ORG-002:** يجب دعم أكثر من بنية: إدارية ووظيفية وتشغيلية وجغرافية ومؤقتة ومصفوفية، مع علاقات منفصلة.  
**القبول:** يمكن أن يملك الموظف مديراً إدارياً ومديراً وظيفياً مختلفين دون خلطهما.

**FR-ORG-003:** كل علاقة تنظيمية أو تكليف يجب أن تحمل تاريخ بداية ونهاية ومصدر اعتماد.  
**القبول:** الاستعلام بتاريخ سابق يعيد البنية التي كانت نافذة آنذاك؛ التعديل لا يمحو العلاقة السابقة.

**FR-ORG-004:** يجب منع دورة أو علاقة متناقضة، مع إمكان نقل الوحدات ودمجها أو أرشفتها بإجراء موثق.  
**القبول:** يرفض النظام دورة في الشجرة، ويعرض سبب الرفض ولا يترك بنية نصف محدثة.

**FR-ORG-005:** يجب توفير عرض شجري وبحث وتنقل بين المرؤوسين والمديرين، مع تعديل مرئي يتحقق قبل الحفظ.  
**القبول:** لا تحفظ إعادة ترتيب السحب والإفلات إذا أنشأت دورة أو تجاوزت نطاق صلاحية المستخدم.

### 6.3 الوظائف والموظفون

**FR-WFM-001:** يجب الفصل بين الشخص وحساب المستخدم والمنصب والمسمى والدرجة والتعيين وعلاقة الإشراف.  
**القبول:** تغيير المسمى لا يغير دور النظام أو الصلاحيات، وحساب الشخص لا يفرض تعييناً واحداً إذا سمحت سياسة المنشأة بتعدد التعيينات.

**FR-WFM-002:** يجب تعريف المناصب والعائلات والدرجات والتصنيف ومستوى الإشراف وحدود المسؤولية كبيانات قابلة للتهيئة.  
**القبول:** يستطيع مدير مخول إنشاء منصب مخصص دون تعديل الشيفرة أو قائمة ثابتة.

**FR-WFM-003:** يجب توليد المسمى حسب قوالب لغوية قابلة للتهيئة ودعم الاستثناء اليدوي.  
**القبول:** يمكن تحديد قالب عربي وآخر إنجليزي، واختيار منصب لا يضاف إليه اسم القسم.

**FR-WFM-004:** يجب حفظ التعيين والانتقال والترقية والتكليف والإعارة والإجازة وإنهاء الخدمة وإعادة التوظيف كسجل تاريخي.  
**القبول:** يمكن استرجاع التعيين النافذ في تاريخ محدد، ولا يمحى تعيين منتهٍ عند إنشاء تعيين لاحق.

**FR-WFM-005:** يجب إتاحة ملفات الموظف والاتصال والعقد والفرع والوحدة والمنصب والمدير والوثائق ضمن الصلاحيات.  
**القبول:** تمنع صلاحية غير مخولة عرض أو تصدير البيانات الحساسة، ويسجل الاطلاع/التغيير وفق سياسة التدقيق المعتمدة.

**FR-WFM-006:** يجب أن تتيح الموارد البشرية إنشاء حسابات الموظفين وربطها بالقسم والمسمى الوظيفي، مع منح صلاحيات ضمن نطاق صلاحيات المدير المفوض فقط.  
**القبول:** لا يستطيع مدير الموارد البشرية إنشاء مدير نظام أو منح صلاحيات خارج نطاقه، ويظل الحساب الوظيفي منفصلاً عن المسمى الوظيفي.

### 6.4 الصلاحيات والتفويض والتدقيق

**FR-SEC-001:** يجب دعم RBAC وABAC بصلاحيات فعل ونطاق سجل ومنشأة وفرع ووحدة وقيمة/حد اعتماد.  
**القبول:** يتحقق كل API خادمياً؛ عدم ظهور الزر في الواجهة لا يعد بديلاً عن الرفض الخادمي.

**FR-SEC-002:** يجب دعم العرض والإنشاء والتعديل والحذف والاعتماد والرفض والطباعة والتصدير والمشاركة والمراجعة والإلغاء والإرجاع.  
**القبول:** لكل فعل قرار صلاحية مستقل، وتختبر مسارات الرفض والنجاح.

**FR-SEC-003:** يجب تعريف تفويض مؤقت ومحدد النطاق والحد المالي والفترة والبديل وسجل الإلغاء.  
**القبول:** ينتهي التفويض تلقائياً بعد تاريخ الانتهاء ولا يسمح بتجاوز حد الاعتماد.

**FR-SEC-004:** يجب تطبيق فصل المهام ومنع تضارب المصالح حسب السياسة.  
**القبول:** لا يعتمد المستخدم العملية التي أنشأها إذا كانت السياسة تمنع ذلك، ويسجل سبب الرفض.

**FR-AUD-001:** يجب تسجيل الفاعل والنطاق والسجل والفعل والقيم السابقة والجديدة والوقت والمصدر والنتيجة.  
**القبول:** يمكن للمراجع المخول تتبع مستند من إنشائه إلى اعتماده وترحيله وعكسه؛ لا يستطيع مستخدم أعمال تعديل سجل التدقيق.

**FR-AUD-002:** يجب تقديم تصدير سجل التدقيق وفق صلاحية مستقلة مع حماية المعلومات السرية.  
**القبول:** كل تصدير يسجل في التدقيق نفسه، وتطبق عليه فلاتر النطاق.

### 6.5 سير العمل والموافقات ومركز القيادة

**FR-WF-001:** يجب أن يسمح محرك عام بتكوين خطوات متسلسلة ومتوازية وشروط حسب القيمة والوحدة والمنصب.  
**القبول:** يمكن تغيير مسار موافقة معتمد من لوحة الإعدادات دون إصدار شيفرة جديد.

**FR-WF-002:** يجب دعم الاعتماد والرفض والإرجاع والإلغاء والإيقاف والاستئناف والتفويض والتصعيد مع سجل كامل.  
**القبول:** لا ينتقل المستند إلى حالة غير مسموحة، وتظهر هوية المعتمد والتوقيت والقرار.

**FR-WF-003:** يجب أن يحمل كل أمر أو مهمة أو طلب رقم مرجعي ومسؤولاً وأولوية وحالة وموعداً وسجل إجراءات.  
**القبول:** يمكن البحث عن الأمر ومتابعة تصعيده، ولا يرى المستخدم المحتوى السري دون صلاحية.

**FR-WF-004:** يجب أن يدعم مركز القيادة الأوامر والتوجيهات والمهام والمشاريع والاجتماعات والقرارات والبلاغات والاعتمادات.  
**القبول:** يمكن تحديد أمر مباشر أو عبر التسلسل الإداري أو جماعي، مع تطبيق قواعد التفويض المعتمدة.

### 6.6 المحاسبة والمالية والامتثال

**FR-AFM-001:** يجب أن يوفر دفتر الأستاذ ودليل الحسابات والقيود اليومية والذمم والصندوق والبنوك والتسويات والمصروفات والإيرادات والأصول والضرائب والإقفال.  
**القبول:** كل قيد متوازن، مرتبط بمستنده المصدر وفترته وشركته، ولا يرحل إذا كانت الفترة مغلقة.

**FR-AFM-002:** يجب ربط الوحدات المصدرية بالمحاسبة عبر خدمة ترحيل واحدة قابلة للتدقيق.  
**القبول:** نجاح العملية يحفظ المستند والقيد وحركة المخزون ذات الصلة كوحدة ذرية أو لا يحفظ أياً منها.

**FR-AFM-003:** يجب دعم العملات والفترات ومراكز التكلفة والموازنات بحسب إعدادات الشركة.  
**القبول:** تعرض التقارير العملة والفترة ومركز التكلفة المستخدم، وتمنع خلط الشركات.

**FR-AFM-004:** لا تعدل القيود المرحلة مباشرة؛ تستخدم قيود عكس أو تصحيح مرتبطة بالأصل.  
**القبول:** تظل القيم الأصلية قابلة للمراجعة بعد التصحيح.

**FR-TAX-001:** يجب اختيار قواعد الضريبة حسب دولة المنشأة ونوع التوريد والإعفاء، لا تثبيت نسبة واحدة عالمياً.  
**القبول:** يعيد الخادم احتساب الضريبة، ويعرض الأساس والنسبة والتقريب لكل بند.

**FR-ZATCA-001:** للشركة السعودية، يجب دعم دورة الفوترة الإلكترونية المطلوبة رسمياً في تاريخ التنفيذ، بما فيها XML وUUID وQR والشهادة والتوقيع وClearance/Reporting والأرشفة وإعادة المحاولة وسجل الردود.  
**القبول:** وثائق الاختبار الرسمية والبيئة التجريبية تثبت صحة الإرسال والاستجابة؛ لا تعرض الفاتورة كمتوافقة قبل نجاح التحقق المطلوب.

**FR-ZATCA-002:** يجب عزل مفاتيح وشهادات التكامل في مدير أسرار، وحفظ مرجعها فقط في قاعدة البيانات.  
**القبول:** لا يظهر السر في سجل التطبيق أو استجابة API أو نسخة غير مصرح بها.

### 6.7 CRM والمبيعات والمشتريات

**FR-CRM-001:** يجب إدارة العملاء والعملاء المحتملين وجهات الاتصال والعناوين والتصنيفات والتفاعلات والزيارات والشكاوى والطلبات والتحصيل.

**FR-SALES-001:** يجب دعم عروض الأسعار وطلبات وأوامر البيع والفواتير والخصومات والمرتجعات والعمولات والأهداف والمناطق.

**FR-SALES-002:** يجب أن يربط كل بند فاتورة بمنتج معرف، ويتحقق الخادم من الكمية والسعر والمخزون والضريبة والخصم.

**FR-PROC-001:** يجب دعم طلبات الشراء وعروض الموردين والمقارنة والتقييم والأوامر والاستلام ومطابقة الفاتورة والسداد.

**معيار القبول المشترك:** لا تستخدم المطابقة بالاسم وحدها لتسوية مالية أو ترحيل؛ يجب أن يكون الربط بمعرف ثابت أو موافقة مراجعة صريحة. تبقى المسودة عند فشل الترحيل مع بيان سبب الفشل.

### 6.8 المخزون والتصنيع والجودة

**FR-INV-001:** يجب دعم الأصناف ووحدات القياس والمستودعات والمواقع الداخلية والوارد والصادر والتحويل والجرد والتسويات والتكلفة والدفعات والحجز وإعادة الطلب.

**FR-INV-002:** يجب تسجيل كل حركة مخزون مع مصدرها وفاعلها ووقتها وموقعها، ومنع الرصيد غير الصحيح حسب سياسة التقييم.

**FR-MFG-001:** يجب دعم BOM وأوامر الإنتاج والمواد الخام والمراحل والتخطيط والعمالة والفاقد وتكلفة الإنتاج.

**FR-QLT-001:** يجب دعم مواصفات وفحوصات المواد والمنتجات والعيوب ورفض الشحنات والإجراءات التصحيحية وسجلات الفحص.

**معيار القبول المشترك:** حركة المخزون والتكلفة لا تتغير إلا عبر عملية مجال معتمدة، وتظل قابلة للتتبع إلى أمرها أو مستندها المصدر.

### 6.9 الموارد البشرية والعمليات الميدانية

**FR-HR-001:** يجب أن يعتمد HRM على محرك التنظيم والتعيينات نفسه، ويقدم العقود والرواتب والحضور والإجازات والمكافآت والجزاءات والتدريب والأداء والتوظيف.

**FR-HR-002:** لا ينشئ HRM أقساماً أو مناصب موازية لمصدر الحقيقة التنظيمي.

**FR-FIELD-001:** يجب دعم المناطق وتوزيع المندوبين والعملاء وجدولة الزيارات والتقويم والخرائط وتقارير الأداء.

**FR-FIELD-002:** يجب تسجيل الموقع عند المهمة المصرح بها وبعد موافقة واضحة فقط، وحساب المطابقة على الخادم وإتاحة المراجعة عند عدم التطابق.  
**القبول:** يرفض النظام إرسال الموقع دون موافقة، ولا يجمعه خارج الزيارة. حد المطابقة المبدئي 50 متراً وفق متطلب سابق، ويحتاج اعتماداً نهائياً لكل منشأة.

**FR-FIELD-003:** يجب أن يمكن تحويل زيارة معتمدة إلى متابعة أو طلب بيع مع بقاء الرابط إلى الزيارة والعميل.

### 6.10 الوحدات المؤسسية والذكاء والتقارير

**FR-OPS-001:** يجب أن يتكامل التواصل والمهام والمشاريع والوثائق والعقود والصيانة والأصول والدعم والمعرفة دون إنشاء نواة بديلة.

**FR-BI-001:** يجب أن يدعم محرك التقارير المالية والتشغيلية وKPI والمقارنة بين الشركات والفروع وتصديراً مقيداً بالصلاحيات.

**FR-BI-002:** يجب أن يظهر التقرير مصدر البيانات والفترة والنطاق والمنهجية، ويستبعد البيانات غير المصرح بها.

**FR-AI-001:** يجب أن يستند AI إلى بيانات فعلية مصرح بها، ويذكر المصدر والفترة ودرجة عدم اليقين عند الحاجة.

**FR-AI-002:** لا ينفذ AI اعتماداً أو ترحيلاً أو تغييراً حساساً دون موافقة بشرية موثقة.

## 7. المتطلبات غير الوظيفية

**NFR-SEC-001:** عزل المستأجرين مطلوب على مستوى API والاستعلام والعلاقات والنسخ الاحتياطي، مع اختبارات سلبية لكل مسار حساس.

**NFR-SEC-002:** HTTPS في الإنتاج، أسرار خادمية، جلسات آمنة، MFA وفق القرار المعتمد، وتحديد معدل الطلبات الحساسة.

**NFR-SEC-003:** لا تسجل كلمات مرور أو رموز جلسات أو مفاتيح أو محتوى أسرار في السجلات.

**NFR-DATA-001:** مفاتيح أجنبية وقيود وفهارس ومعاملات مناسبة، حذف منطقي عند الحاجة، وفعالية زمنية للعلاقات التاريخية.

**NFR-DATA-002:** كل ترحيل له نسخة احتياطية مجربة وخطة رجوع وتقرير نتيجة، ولا يطبق تلقائياً على بيانات الإنتاج.

**NFR-UX-001:** واجهات عربية وإنجليزية، RTL/LTR، متجاوبة مع الجوال واللوحي وسطح المكتب، مع حالات خطأ وتحميل وصلاحية واضحة.

**NFR-UX-002:** دعم إمكانية الوصول الأساسية والتنقل بلوحة المفاتيح وعناوين ونماذج قابلة للفهم.

**NFR-REL-001:** العمليات الحساسة آمنة لإعادة المحاولة ولا تنشئ قيوداً أو حركات مزدوجة.

**NFR-OBS-001:** سجلات ومقاييس تشغيل منقحة من البيانات الحساسة، مع تنبيه للأخطاء المتكررة وفشل التكامل.

**NFR-PERF-001:** أهداف زمن الاستجابة والحجم المتزامن والتوافر **TBD**؛ تحدد قبل اختبار الأداء والإنتاج ولا تخمن هنا.

**NFR-LOC-001:** دعم العملة واللغة والمنطقة الزمنية والتقويم بحسب سياسة المنشأة، مع حفظ التوقيت المرجعي المناسب.

## 8. العمليات الأساسية

### 8.1 دورة الشراء

طلب شراء ← تحقق من المخزون والسياسة ← عروض ومقارنة ← موافقات حسب الحد/المنصب ← أمر شراء ← استلام وفحص جودة عند الحاجة ← تحديث المخزون ← مطابقة فاتورة المورد ← قيد مستحقات ← سداد معتمد ← تدقيق وإشعارات.

### 8.2 دورة البيع

فرصة/عميل ← عرض سعر ← موافقة الخصم إن لزم ← طلب بيع ← التحقق من المخزون ← تجهيز وتسليم ← فاتورة وضريبة ← موافقة وترحيل ← قيد تحصيل/ذمم ← مرتجع/عكس عند الحاجة.

### 8.3 دورة التغيير التنظيمي

طلب نقل/تكليف ← تحقق الصلاحية والتعارض ← اعتماد وفق سياسة المنشأة ← علاقة جديدة بتاريخ سريان ← إغلاق العلاقة السابقة بتاريخ صحيح ← تحديث عرض الهيكل والصلاحيات المشتقة صراحة فقط ← إشعار وتدقيق.

### 8.4 دورة الزيارة

تعيين من مسؤول مخول ← جدول وموقع عميل معروف ← عرض المهمة للمندوب ← طلب إذن موقع عند الوصول ← تسجيل مرة واحدة ← مطابقة/مراجعة ← تقرير ومتابعة أو طلب بيع ← حفظ التدقيق دون تتبع خارج المهمة.

## 9. نماذج البيانات الأساسية

تشمل الكيانات المستهدفة، دون تقرير نهائي للعلاقات قبل المرحلة D:

Groups, Companies, Branches, Locations, OrganizationalUnitTypes, OrganizationalUnits, OrganizationalRelationships, People, Users, Memberships, Roles, Permissions, Policies, JobFamilies, JobLevels, JobTitles, Positions, PositionAssignments, EmployeeAssignments, ReportingRelationships, Delegations, Workflows, WorkflowSteps, Approvals, Commands, Tasks, Projects, Documents, Conversations, Messages, Notifications, AuditLogs، ثم كيانات كل وحدة.

كل علاقة أعمال تحتاج معرفاً ثابتاً، ونطاق منشأة واضحاً، وقيود مرجعية، وحقول سريان/حالة حيث يلزم. تصميم ERD والفهارس مسؤولية المرحلة D.

## 10. معايير القبول على مستوى المنتج

لا يعد الإصدار المؤسسي جاهزاً حتى:

1. تمر اختبارات عزل منشآت ومجموعات متعددة من API وقاعدة البيانات والتقارير.
2. يمكن إعداد نوع تنظيم ومنصب ومسار موافقة دون تغيير الشيفرة.
3. تحفظ التعيينات والعلاقات التاريخية ويمكن الاستعلام عنها بتاريخ سابق.
4. تنفذ الصلاحيات على الخادم حسب الفعل والنطاق ولا ترتبط بالمسمى وحده.
5. ترتبط المستندات المصدرية بالمخزون والقيود والتدقيق وفق معاملات متسقة.
6. تخضع القيود المرحلة للتصحيح عبر عكس موثق فقط.
7. تظهر كل ميزة بوضوح كفعالة أو غير مفعلة أو غير متاحة؛ لا بيانات تجريبية على أنها حقيقية.
8. تنجح اختبارات النواة والتكامل والعزل وعمليات الاستعادة، ويجتاز بناء الإنتاج وفحوصات الأمن.
9. تستوفي المتطلبات التنظيمية للدولة المعتمدة باختبارات رسمية قبل تفعيل التكامل.
