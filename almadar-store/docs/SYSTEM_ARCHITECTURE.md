# معمارية النظام — مسودة المرحلة B

**الحالة:** مسودة للمراجعة والاعتماد  
**المرجع الحالي:** [تقرير تدقيق المشروع](./PROJECT_AUDIT.md)

## القرار المعماري المقترح

الاستمرار كتطبيق **Modular Monolith** باستخدام Next.js وPostgreSQL/Supabase، مع فصل واضح بين واجهات العرض، واجهات API، خدمات المجال، ومستودعات البيانات. لا تُجزّأ المنظومة إلى خدمات مستقلة قبل وجود حاجة تشغيلية مثبتة.

تظل قاعدة البيانات مصدر الحقيقة للعمليات. لا تنفذ الواجهة حسابات أو موافقات حساسة على أنها نهائية؛ يتحقق الخادم من الهوية والصلاحيات والبيانات، وتنفذ قاعدة البيانات المعاملات التي يجب أن تكون ذرية.

## الطبقات

1. **واجهة المستخدم:** صفحات RTL/LTR، مكونات مشتركة، ونماذج مرتبطة بحالات تحميل/خطأ/صلاحية واضحة.
2. **واجهات التطبيق:** API موحدة لكل وحدة، تتحقق من الجلسة والمنشأة والصلاحية والمدخلات، ولا تكشف مفاتيح قاعدة البيانات.
3. **مجالات الأعمال:** خدمات مستقلة للمحاسبة والمبيعات والمخزون والموارد البشرية وغيرها؛ لا تستدعي وحدة تفاصيل التخزين الخاصة بوحدة أخرى.
4. **النواة المؤسسية:** المستأجرون والمنشآت والفروع والهوية والعضويات والسياسات وسير العمل والتدقيق والإشعارات والوثائق.
5. **البيانات والتكاملات:** PostgreSQL بمعرفات وعلاقات وقيود واضحة؛ JSONB للبيانات المرنة المساندة فقط، لا بديلاً عن الكيانات والمعاملات الجوهرية.

## حدود الوحدات

- لكل وحدة واجهات خدمة ومخططات إدخال/إخراج واضحة.
- تمر العمليات المشتركة من خدمات النواة بدلاً من نسخ منطق المستخدم أو الصلاحيات داخل كل وحدة.
- تعتمد المحاسبة على أحداث تشغيل موثقة، وتنتج قيوداً متوازنة ضمن معاملة واحدة مع المستند المصدر.
- يسجل كل انتقال حالة أو اعتماد في سجل تدقيق؛ ولا تعدل المستندات المرحلة مباشرة.
- تستخدم الأحداث/Outbox للتكاملات غير المتزامنة، مع مفاتيح idempotency وإعادة محاولة محدودة.

## حدود العزل والاتساق

- كل سجل أعمال يحمل `company_id`، وتحدد الجلسة المنشأة النشطة من عضوية مخولة.
- تتم مقارنة المنشأة والملكية والصلاحية على الخادم قبل كل قراءة أو تغيير.
- المفتاح الإداري لـSupabase يبقى في الخادم فقط؛ وجود RLS وحده لا يكفي للعزل ما دام الخادم يستخدم service role.
- عمليات الترحيل المالي والمخزني والقبول النهائي تستخدم معاملات وقفل/قيود قاعدة البيانات عند الحاجة.
- ترحيل البيانات يتم على مراحل متوافقة، مع نسخة احتياطية مجربة وخطة رجوع قبل أي تغيير بنيوي.

## قابلية التكوين

تكون أسماء مستويات التنظيم والمناصب وسير العمل والأدوار قابلة للإدارة من بيانات المنشأة وسياساتها، لا من قوائم ثابتة في الواجهة. لا يؤدي تغيير المسمى الوظيفي إلى تغيير الصلاحيات تلقائياً.

## قرارات تحتاج اعتماداً

- هل المستأجر الأعلى هو المجموعة، أم الشركة؟ وكيف ترتبط الشركات التابعة والمنشآت المستقلة؟
- نطاق تعدد الفروع والمخازن ومراكز التكلفة لكل سجل.
- مصدر المصادقة النهائي: المصادقة الحالية أو Supabase Auth أو موفر مؤسسي آخر.
- أسلوب حفظ المرفقات والوثائق، وفترة الاحتفاظ بالتدقيق.
- الدولة الأولى للإطلاق والمتطلبات الضريبية والتوقيع الإلكتروني.

جرى إعداد مسودة تصميم نموذج البيانات وخطة الترحيل في [DATA_MODEL.md](./DATA_MODEL.md). لا تبدأ تغييرات قاعدة البيانات أو استبدال نموذج التخزين قبل اعتماد التصميم والقرارات ذات الصلة.
